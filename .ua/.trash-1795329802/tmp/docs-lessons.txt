README.md|这是 mcp-go 的项目介绍与使用手册。先读安装和最小服务端示例，建立对工具注册与传输启动的认识，再切换到导览第一步的进程内示例。
75-83|认识库的定位|这段列出库的目标，包括通过高层接口减少搭建 MCP 服务端所需的样板代码。后续例子展示哪些能力由库提供，哪些仍由应用编写。
109-200|动手写计算工具|安装之后，示例创建服务端、声明计算工具并注册处理函数。对比除以零时返回的工具错误与启动服务失败时返回的 Go 错误，可以看到业务结果和进程错误的区别。最后通过 `ServeStdio` 对外提供服务。
201-237|区分三种能力|资源负责暴露数据，工具负责执行操作，提示词负责提供可复用的交互模板。紧接着的服务端章节说明如何用构造选项声明能力。
645-660|选择示例与传输|示例索引按主题链接任务工具、类型化参数和上下文等用法，传输章节列出 stdio、SSE 与 Streamable HTTP。导览中的进程内示例另用了库提供的同进程客户端，可直接观察协议调用过程。
983-1018|寻找扩展点|请求钩子覆盖请求生命周期，处理器中间件只包裹特定类别的处理器。这里还记录了重新生成服务端钩子与请求派发代码的入口，便于从生成产物回查模板。
examples/in_process/main.go|这个示例在同一个 Go 进程中运行 MCP 服务端与客户端。它按注册、启动、初始化、列出工具、调用工具的顺序走过一条完整路径。
14-35|注册示例工具|处理器接收上下文和 `CallToolRequest`，返回值为固定文本。构造出的 `Tool` 提供名称和描述，`AddTool` 再把描述与执行函数绑定在同一个注册项中。
37-76|启动并初始化客户端|使用 `NewInProcessClient` 直接连接服务端对象，给传输启动设置五秒超时。随后用原始上下文调用 `Initialize`，并保存返回的服务端信息。
78-100|列出并执行工具|先通过 `ListTools` 查看已注册的工具，再把 `dummy_tool` 填入调用请求。最终打印的是工具结果的 `Content`，它与构造时声明的工具描述对应不同的阶段。
mcp/types.go|这个文件定义客户端与服务端共享的协议类型，涵盖 JSON-RPC 消息、能力声明和 MCP 内容类型。导览第二步从消息信封和初始化载荷出发，建立读取两端实现所需的词汇。
208-345|区分请求与通知|通用请求参数可以包含 `_meta`。通知参数的自定义编解码将元数据与其余字段合并到同一 JSON 对象，并在读取时分开保存。
361-480|对齐请求与响应|带编号的请求与对应的成功或错误响应都使用 `RequestId`。自定义解码先尝试整数的精确表示，以避免全部经由 `float64` 时丢失大整数的低位。
602-701|读取初始化契约|初始化请求说明客户端身份、协议版本与能力，响应给出服务端身份、选定版本和可用能力。能力结构多用可省略的指针字段，这使字段缺失与存在但采用默认值可以区分。
782-912|识别分页与资源请求|分页请求用 `Cursor` 表示起点，分页结果用 `NextCursor` 表示后续位置。资源相关结构共享分页约定，并单独声明读取、订阅、退订和更新通知的载荷。
1183-1452|识别采样内容类型|采样请求声明消息和相关参数，内容用 `Content` 接口及具体类型表示。文本、图片、音频和工具交互内容各自拥有结构字段，读返回值时要按具体内容种类处理。
mcp/tools.go|这个文件定义工具的描述、调用载荷、结果与参数模式。导览第二步可从 `NewTool` 向前追到序列化契约，向后追到属性选项如何写入 Schema。
44-120|理解工具请求和结果|请求参数保留普通 `Arguments` 和原始 JSON 字节两种形式，`BindArguments` 优先使用原始字节填充 Go 结构体。结果把多态的 `Content` 与可选的结构化内容分开，并用 `IsError` 标记业务执行错误。
616-708|阅读结果编解码|编码显式构造内容数组，并按条件加入结构化内容和多轮交互字段。解码逐条调用 `UnmarshalContent`，同时保留结构化 JSON 原文与解码后的值。
734-827|在两种模式表示间选择|工具定义可使用结构化 Schema 或原始 JSON Schema。序列化会检查两种表示是否同时设置，并按照字段类型与是否存在决定是否输出。
1195-1288|使用工具构造选项|构造函数先建立对象形式的输入模式和默认注解，再依次执行调用方传入的选项。由 Go 类型推导输入模式时，选项清空已有的结构化类型标记并设置生成的原始 JSON Schema。
1571-1696|声明属性与必填项|整数、布尔值等构造选项先建立各自的属性 Schema，再应用传入的属性约束。最终 `setInputProperty` 把属性内部的临时必填标记移到对象顶层的 `Required` 列表。
client/client.go|这里把类型化 MCP API 转为传输层请求，并维护协议版本、能力和请求编号。导览第三步可用 `Initialize` 与 `CallTool` 串起客户端的主要职责。
184-225|接上传输与回调|构造函数保存传输对象并应用选项，启动时由底层传输建立连接。通知处理器在锁内复制再在锁外调用，支持双向通信的传输还会得到客户端入站请求处理器。
257-323|统一构造和发送请求|公共发送路径检查初始化状态、填充协议元数据和请求头、分配编号并记录追踪信息。随后它将传输错误和 JSON-RPC 错误转换为不同的 Go 错误路径，并在上下文取消时根据请求情况尝试通知服务端。
399-427|选择协议发现流程|先合并身份与能力并确定首选版本，再按版本和传输配置决定是否尝试现代发现流程。发现成功后，客户端更新状态并将发现结果适配为现有的初始化结果类型。
430-502|完成传统握手|传统路径发送 `initialize`，验证并记录响应版本，再发出 `notifications/initialized`。当调用者没有指定旧版版本时，这条路径请求支持握手的最新版本。
711-770|从工具列表走向调用|分页列表会过滤带无效头部注解的定义，并缓存剩余定义供之后的工具请求使用。调用入口注入元数据并进入通用多轮循环，每一轮才委托给单次工具调用函数。
server/server.go|这是 MCP 服务端的核心注册表与业务处理层。导览第四步可对照这里的工具注册和执行逻辑，以及生成的请求派发入口。
758-800|构造服务端状态|构造函数建立资源、提示词、普通工具与任务工具的独立注册表，并准备默认补全和追踪实现。最后应用传入选项，让调用者声明能力或替换默认实现。
1045-1130|注册工具及其能力|单个工具被转换成包含描述与处理函数的 `ServerTool`，再进入批量注册逻辑。批量注册先检查名称冲突、Schema 默认规则和参数注解，再更新完整批次，最后可能广播工具列表变化。
2202-2283|查找工具并选择执行模式|调用优先查找会话工具，再查全局普通工具和任务工具。找到的工具仍需要通过过滤，并根据请求的任务参数和声明的任务支持模式决定是否走异步任务路径。
2285-2348|运行处理器并衔接多轮请求|启用输入校验时，先检查原始参数，再以逆序包裹中间件并调用处理器。现代客户端可接收补充输入请求并重试，旧协议的补充输入可由服务端协调并再次调用处理器。`nil` 结果被转成明确的内部错误。
server/request_handler.go|这是由模板生成的 JSON-RPC 派发器，负责从原始消息进入类型化处理函数。导览第四步借它对照信封检查、协议识别、工具调用钩子和响应构造。
15-100|检查消息信封|入口把服务端实例写入上下文，再读取版本、方法、编号和参数元数据。编号有单独的数值解码逻辑，之后检查标准字段名和 JSON-RPC 版本。
102-152|分开通知与普通请求|无编号的消息进入通知处理并且不生成正常响应，具有结果载荷的入站响应同样提前处理。剩余请求根据上下文登记在途编号，再运行初始化钩子并获取请求头。
153-206|识别协议并布置观测|请求的 `_meta` 用于识别现代协议，现代路径还会核对版本和标准请求头。随后设立追踪和日志回调，并延迟为返回结果添加协议所需的元数据。
539-590|派发工具列表和调用|两条工具分支先检查服务端能力，再反序列化到具体请求结构。成功路径把头部复制给请求、运行前置和后置钩子并构造成功响应，失败路径运行错误钩子并转成 JSON-RPC 错误。
client/transport/streamable_http.go|这个传输用 HTTP POST 发送 JSON-RPC，同时接受 JSON 响应或同一请求内的 SSE 流。导览第五步可对照服务端路由，判断版本、会话与流式读写在哪一层处理。
768-854|发送请求与分类状态|请求首先编码为 JSON，再通过 POST 表明接受 JSON 和事件流两种响应。HTTP 错误按场景保留授权提示、旧版传输兼容信号或可解析的 JSON-RPC 错误体。
856-911|处理会话与内容类型|传统初始化可以从响应头保存会话编号。随后按内容类型选择 JSON 解码或 SSE 读取，并在成功的发现或初始化响应后更新连接状态。
1041-1141|从 SSE 事件读出结果|读取协程区分通知、服务端发起的请求和正常响应，前两种分别交给对应回调。调用方等待响应、读取结束或取消，旧协议还可以携最后事件 ID 恢复满足条件的流。
server/streamable_http.go|这个文件把 MCP 核心派发器接入 HTTP，同时为不同协议版本组织会话和 SSE。与导览中的客户端传输对照，可以看出 HTTP 响应状态、连接状态和 JSON-RPC 结果之间的关系。
446-504|从 HTTP 路由到 MCP|入口做主机保护和 CORS 检查，并处理受保护资源元数据端点。读入并限制 POST 内容之后，依据 HTTP 方法选择对应处理函数。
673-739|识别 POST 消息与协议版本|POST 要求 JSON 内容并先解析外层消息，以便区分请求和客户端发送的响应。现代协议由请求头和元数据识别，并与旧版需要会话的分支分开处理。
870-923|准备流式输出|请求上下文保存头部和订阅有关的状态。只有响应写入器支持流时才能升级到 SSE，有事件存储且协议沿用旧版会话时才允许保存可恢复的事件。
1163-1213|输出最终响应|已经升级到 SSE 的请求继续写事件，其他请求走普通 JSON 响应。现代 JSON 响应会根据 JSON-RPC 错误调整 HTTP 状态码，传统初始化则可在响应头里带回会话编号。
1232-1284|接收旧版独立事件流|旧版 GET 可打开通知流，也可凭 `Last-Event-ID` 进入恢复分支。现代协议拒绝独立 GET，改由协议方法 `subscriptions/listen` 建立订阅。
1442-1473|终止旧版会话|旧版 DELETE 使用会话管理器终止指定会话，成功后清理会话状态。现代请求在入口被拒绝，因为该协议版本不通过 HTTP 会话编号维持状态。
